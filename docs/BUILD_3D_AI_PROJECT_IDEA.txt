01. THE CENTRAL PROJECT IDEA

Build 3D AI should become an independently controlled 3D creation and production
studio. It should help a creator turn an idea, reference image, or existing
licensed asset into an editable 3D asset that can actually be reused in a game,
animation, advertisement, educational scene, or Blender production.

The long-term experience is:

  Describe or upload an idea
  -> create or import geometry
  -> inspect and correct it
  -> prepare materials and useful mesh structure
  -> optionally rig and animate it
  -> place it in a reusable scene
  -> export a validated production asset.

The first dependable promise should be narrower: help a creator obtain,
inspect, organize, and export a usable 3D asset, while clearly showing the
remaining work. A beautiful front-view image is insufficient if the model
breaks when rotated, exported, or animated.

The project's longer-term specialty should be reusable stylized adult
characters and environments for Blender-based storytelling. The broader asset
platform remains valuable to other creators as well. Start with supported
objects and a carefully constrained character workflow; expand after measuring
quality and cost.

A possible product statement is:

  "Create 3D assets you can inspect, improve, and keep using. Build a consistent
  cast, props, and places for your own creative world."

AI can assist asset creation, editing, and planning. Final animation can still
be produced from real meshes, rigs, cameras, lighting, and renders. The product
does not need to depend on AI-generated final video to serve that vision.


02. THE PROBLEM AND THE FIRST CUSTOMERS

A creator's difficult work often starts after initial generation. The creator
must discover whether an asset has usable unseen surfaces, reasonable material
maps, editable parts, working joints, compatible exports, and consistent scale.
Characters may have attractive renders but unusable eyelids, fused clothing,
poor hands, or no mouth interior. A lower polygon count does not fix these
problems automatically.

Another problem is continuity. A creator making multiple scenes needs the same
character, costume, furniture, and location to remain recognizable. Recreating
an asset from a new prompt can change its identity or proportions.

The initial customer hypothesis is a small creator or independent studio using
Blender who needs reusable stylized props and, eventually, recurring characters.
Indie game developers and visualization artists are adjacent customers, but
supporting every engine and professional workflow immediately would dilute the
first release.

Their useful outcomes are concrete:

- Less manual cleanup time before an asset is usable.
- Fewer failed imports, missing textures, and broken animation attempts.
- A reusable private asset library with clear versions and provenance.
- A guided path for people who are not expert technical artists.
- Predictable spending and an honest explanation of output limitations.

The owner should validate these hypotheses through interviews and small paid
pilots. Interest in an AI demonstration does not establish willingness to pay
for a production tool.


03. WHAT ALREADY EXISTS IN THIS PROJECT

The repository already contains substantial first-party infrastructure. Preserve
it and improve it rather than replacing it with another starter application.

A. Private product API and durable work records

The product API implements operator-provisioned users and API keys, private
projects, durable text/image job records, owner-based access checks, bounded
image processing, idempotent admission, rate limits, and active-job limits.
Normalized input images can survive process restarts through database storage.

The worker implements claims and fencing to reduce duplicate local processing.
It distinguishes uncertain upstream submission from known failure. It does
not blindly resubmit potentially billable generation after a lost response.
Only queued jobs can currently be canceled locally; canceling remote GPU work
is not an implemented general capability.

B. Web studio and GLB viewer

The first-party Next.js studio supports private API-key login, projects, job
history, status/error displays, storage usage, an approved-model state, and a
Three.js-based GLB viewer. Its browser-facing backend keeps the persisted user
key in an HttpOnly cookie and restricts proxied routes.

The viewer provides orbit/zoom, reset, wireframe, and geometry statistics. The
private login mechanism is not complete public signup, account recovery,
verification, deletion, or commercial identity lifecycle.

C. Artifact storage and integrity

Filesystem storage, optional S3-compatible storage, persistent storage quotas,
read-only inventory scanning, and a copy-only filesystem-to-S3 migration path
exist in code. Downloads check ownership and revalidate GLB structure and
checksums. A real cloud bucket and production storage operations have not been
proven by this work; synthetic storage tests do not establish those results.

D. Identity foundations

Immutable external-identity mapping and optional issuer/audience/JWKS-based
trusted JWT authentication exist. The external authentication path is disabled
by default. It is a foundation for further identity work, not a completed public
browser account system. Some older documentation understates this newer code.

E. Controlled model gateway and packaging

The gateway implements an upstream API contract, model approval checks, bounded
GLB verification, and an explicit-spend smoke-runner interface. A first-party
OBJ-plus-PNG-to-textured-GLB packaging component has synthetic CPU coverage.
Packaging a texture does not prove a complete physically based material set or
that the generated texture looks correct from every angle.

F. Candidate model preparation

A pinned TripoSR qualification preparation path exists with source checks,
checkpoint verification requirements, controlled loading, and CPU contracts.
It is a candidate for a real qualification experiment, not a validated
production engine. The default approved-model list is still empty.

G. Organized reference material

The source snapshots now live in third_party/3daigc-api/ and
third_party/triposr/. The supplied rigging examples and demos live under
assets/reference/autorig/. Their presence is reference material, not proof
that this project's generator or auto-rigger runs.

The 3DAIGC source archive lacks its declared submodule source. Some bundled
wheels carry noncommercial restrictions. The example asset bundle has no
supplied license. These remain RESEARCH_ONLY, subject to their actual terms.

H. Verification already performed in this conversation

Earlier environment setup passed 136 first-party Python tests, four web unit
tests, TypeScript checks, a production web build, and six browser contract
tests. The archive organization change subsequently passed the Python tests,
web unit tests, TypeScript checks, and extraction-integrity checks again.
The browser fixtures are synthetic. These results were not rerun just to write
this document, and they do not prove AI generation quality or production scale.

The practical description of the current project is:

  A tested early product foundation with a candidate inference integration;
  genuine GPU generation and commercial production readiness remain unproven.

There is no verified real-model generation run, model-quality benchmark,
AI-generated asset imported into Blender, public paid service, trained custom
model, or production deployment established by this repository snapshot.


04. WHAT EXISTS ELSEWHERE THAT WE SHOULD REUSE

Do not spend the project's limited effort rebuilding established infrastructure
or mature graphics algorithms without a measured reason.

Reuse categories include:

- Blender for serious scene assembly, animation, inspection, and rendering.
- Three.js and the existing viewer for browser inspection.
- Suitable reviewed UV, mesh, and export utilities for processing.
- Existing identity, payment, database, and observability building blocks.
- Legally usable pretrained generation models behind isolated adapters.
- Reviewed rigging and retargeting technology where it fits the target assets.

The repository already studies 3DAIGC-API as an upstream contract/reference and
TripoSR as a first qualification candidate. UniRig, SkinTokens, xatlas,
glTF Transform, and other catalogued projects are evaluation candidates, not
automatic product integrations. The existing reuse and license audits should
be the starting point for selection.

Meshy and Tripo are examples of relevant market baselines recorded in project
planning. This document does not claim their current prices, feature sets,
relative quality, or future roadmaps have been checked. Evaluate actual dated
versions on permitted inputs before making competitive claims.

For every dependency, review source, weights, runtime libraries, data rights,
service terms, and deployment requirements separately. Public availability is
not equivalent to unrestricted commercial permission. Upgrading to a newer
AI model must repeat that review and the performance evaluation.


05. WHAT MAKES THE PRODUCT WORTH BUILDING

The strongest differentiation is a reliable route from an asset idea to
continued use in production. Five proposed capabilities support that goal.

A. A clear readiness report

Every asset should show what was actually checked: geometry, material presence,
external resources, Blender import, and, where relevant, deformation. Distinguish
"file is structurally valid" from "artist approved" and "animation tested."
A check that has not run must remain visibly unverified.

B. An understandable asset history

Store the source input, rights notes, model revision, generation settings,
processing steps, and exported versions. Let a creator branch an asset version
inside the product, compare alternatives, and return to an earlier result.
This is proposed product versioning, beyond the existing project/job history.

C. Stable recurring characters

Once a character is accepted, reuse the actual mesh, rig, materials, and
approved variants. Maintain identity through persistent assets and constraints;
do not rely solely on generating a similar face repeatedly.

D. Preservation during editing

An edit should identify what it is intended to preserve: face, proportions,
rig, material layout, or silhouette. Show a comparison and record any damage.
Until local generative editing is reliable, accomplish supported changes with
ordinary mesh/material operations and human review.

E. Completion cost rather than generation speed alone

Measure the time and total cost required to obtain an accepted usable result.
A faster generator can still be a worse tool if it creates expensive cleanup.
This metric connects engineering effort to the customer's actual problem.

These are proposed advantages to earn through evidence, not established market
leadership or guaranteed protection from competition.


06. A COMPLETE CUSTOMER JOURNEY

Imagine a creator needs a reusable wooden chair for a stylized room.

1. The creator opens a private project and selects a supported asset type.
2. They upload a permitted image or import a licensed existing model. Text input
   becomes available only when a qualified text-capable pipeline exists.
3. The studio explains supported inputs, estimated resource cost, and important
   uncertainty, including inferred hidden surfaces.
4. The user starts the task and receives persistent progress and failure states.
5. The result opens in the viewer with multiple-angle inspection, dimensions,
   geometry statistics, and material information.
6. The system flags thin or missing components and identifies checks it cannot
   perform. The creator can request a supported revision or fix it in Blender.
7. An optimization operation creates a new version while retaining the original.
8. An export preset produces a validated GLB for the supported downstream path.
9. The asset remains in the creator's library and can be reused across scenes.

A character journey adds independent geometry, body-rig, face-rig, motion, and
render checks. The interface should explain those extra stages rather than
labeling every generated human-shaped mesh "animation ready."


07. THE FIRST USEFUL RELEASE

Recommended first release: a private image-to-asset workflow for a limited set
of stylized props, connected to the existing studio, with honest validation and
Blender export proof. It should demonstrate one complete real pipeline before
expanding the menu of model choices.

In parallel, explore a constrained character workflow using rights-cleared,
artist-prepared base characters. This can advance the long-term specialty
without waiting for arbitrary image-to-perfect-character generation.

Include in the initial release:

- One qualified generation path with a declared supported input range.
- Private projects, job history, useful error reporting, and verified downloads.
- A real textured GLB inspected in both browser and Blender.
- Preserved originals and simple, reversible processing where validated.
- Provenance, known limitations, and actual resource measurements.
- Spending controls appropriate to the private pilot.

Defer from the initial release:

- Universal character auto-rigging and cinematic facial performance.
- Automatic full episodes or arbitrary explorable worlds.
- Training a general 3D foundation model from scratch.
- Every export format, marketplace, payment tier, and game engine at once.
- Claims of best-in-market output quality or guaranteed creative ownership.

For public access, complete identity lifecycle, privacy/deletion handling,
billing integrity if charging, operational monitoring, and deployment checks
before opening the service. A private operator-provisioned pilot and a public
commercial release have different readiness requirements.


08. THE FULL PRODUCT: CREATION, EDITING, AND REUSABLE ASSETS

The longer-term product can expand through independent capabilities.

Creation:
- Image-to-3D for declared object categories.
- Text-to-3D through a qualified native model or an explicitly labeled
  text-to-image-to-3D chain. Store the intermediate image and its provenance.
- Multiple views with guidance for consistent references and camera coverage.
- Import of existing licensed assets as a useful route independent of AI.

Mesh preparation:
- Geometry diagnostics, normal repair, bounded cleanup, and component review.
- UV inspection, material assignment, texture inspection, and validated baking.
- Target triangle budgets, levels of detail, and protected high-detail originals.
- Retopology evaluated separately for static assets and deforming characters.
- Part separation and local edits where results preserve useful structure.

Material editing:
- Named material regions and selective color/texture adjustments.
- Preview under consistent lighting and preservation of surface boundaries.
- Real metallic/roughness/normal maps where the pipeline actually produces
  them; do not relabel a single color texture as complete PBR reconstruction.

Library and collaboration:
- Searchable assets, versions, collections, thumbnails, and provenance.
- Later team access, comments, approved versions, and role-based permissions.
- Import/export presets tested against actual downstream application versions.

New controls should expose artistic intentions such as "preserve face detail"
and "reduce background prop complexity." Resource-specific settings can remain
available to advanced users when they help make a meaningful decision.


09. THE CHARACTER AND FACIAL-ANIMATION VISION

The flagship long-term outcome is a recurring stylized adult character that
remains recognizable across poses, clothing variants, expressions, and scenes.

A practical route has three stages.

Stage A: artist-prepared templates

Use licensed base meshes, known topology, tested rigs, and controlled proportion
or material changes. This offers a stronger continuity foundation than
regenerating an entire character every time. The user still needs a clear
account of the template's rights and customization limits.

Stage B: generation plus guided preparation

Bring generated characters through geometry review, part separation,
retopology, UV work, and rig fitting. Let a creator correct landmarks or select
a compatible topology template. Retain expert review for difficult joints,
hair, layered clothing, hands, and facial structure.

Stage C: progressively learned assistance

Evaluate trained assistance for rig fitting, skin weights, expression transfer,
and local edits after the team has suitable data and a reliable benchmark.
Keep corrective editing available and expose failures rather than hiding them.

Treat body animation and facial performance as separate capabilities.

Body acceptance should include shoulder, elbow, hip, knee, and wrist motion;
foot contact; scale; clipping; and distortion under representative poses.

Facial acceptance should separately evaluate:
- Eyeball placement and gaze.
- Eyelid geometry and blinking over the eye surface.
- Brow movement, smile, frown, and cheek deformation.
- Jaw motion, teeth, tongue, and mouth interior when required.
- Speech shapes and transitions appropriate to supported languages.
- Expression combinations and preservation of character identity.

A skeleton or walk cycle does not establish these facial capabilities.
Lip synchronization does not establish acting quality or believable emotion.
Human animators and technical artists should define the target standard.

The owner's adult-proportion character goal can become a benchmark category:
consistent grown-person proportions, expressive eyes, useful hands, controlled
clothing, and stable identity. It is a creative acceptance target, not a claim
that a currently supplied example asset meets it.


10. ENVIRONMENTS AND SCENE PRODUCTION

Start environments with reusable modular sets: rooms, walls, doors, furniture,
streets, and props with consistent scale and separate editable objects.

A location should retain object identities and placements across scenes.
Creators should be able to move a chair, change lighting, open a door if the
asset supports it, and use different cameras without rebuilding the set.

Later assistance can propose layouts from descriptions, references, or rough
plans. Validate navigable space, intersections, scene complexity, and intended
camera views. Treat object interaction and simulation as additional problems.

An attractive rendered scene is different from a coherent editable scene graph.
Gaussian splats can be useful for backgrounds or specific viewing experiences,
but they should have a separate representation label and editing contract.
They are not automatically individually editable polygon objects.

Offer a Blender-oriented production path before attempting a complete browser
replacement for Blender. Integration and dependable transfer can be more useful
than duplicating a mature digital content creation application.


11. AN AI ASSISTANT INSIDE THE STUDIO

A later assistant could translate creative intent into a reviewable sequence:

  "Use this approved character, add a navy jacket, preserve the face and body
  proportions, place her in the saved office, and prepare a short walk test."

The assistant should explain which steps use existing assets, which invoke
new generation, what may change, and the expected cost. Use bounded operations,
versioned outputs, visible progress, and a clear way to reject a result.

It may help with search, parameter suggestions, diagnostics, scene assembly,
export selection, and draft camera or animation plans. It should act through
restricted product tools, not unrestricted execution of uploaded instructions
or arbitrary code in a privileged runtime.

Reversible material edits can be automated more freely than expensive
regeneration, destructive deletion, publication, or training. Any spending
must stay within explicit user-approved limits. The assistant should report
uncertainty and ask for the minimum necessary artistic decision.

Natural-language control is an interface improvement. It does not by itself
solve geometry, model licensing, animation correctness, or scene continuity.


12. QUALITY, CONFIDENCE, AND EVIDENCE

Create separate quality profiles for supported uses:

- Static background prop.
- Close-up asset.
- Rigid interactive object.
- Body-animated character.
- Facial close-up character.
- Editable environment component.

Each profile needs different checks. A static background chair should not need
facial-animation criteria, while a talking character needs much more than a
successful GLB parse.

Use three kinds of evidence:

Technical: file integrity, bounded resources, geometry, UV/material presence,
import success, and supported deformation checks.

Artist: all-angle appearance, style fit, identity, expression, texture quality,
and manual cleanup required.

Operational: success/failure rate, latency distribution, VRAM, total cost per
accepted asset, privacy, recovery, and support effort.

Keep generated failures in the benchmark. Record model and runtime versions,
input rights, parameters, hardware, timing, and actual output hashes. Prefer
held-out examples and blind comparisons where practical.

A proposed 100-item release benchmark already appears in project planning.
Its aspirational 95% valid-job target is not an observed result. Report sample
size and uncertainty; even a strong 100-run result is not proof of universal
reliability or a production service-level guarantee.

Better metrics include median artist cleanup time, accepted-asset rate,
identity drift across allowed edits, deformation failures, and actual import
success. Do not compress all of these into an unexplained "AI quality score."


13. WHAT IS NOT POSSIBLE, NOT RELIABLE, OR NOT AVAILABLE YET

These categories matter. Some limitations are current project gaps; others
require difficult research; several cannot be removed by a more fluent model.

A. Information that the input does not contain

A single ordinary photograph cannot uniquely determine every hidden surface,
internal structure, exact material property, or physical dimension. Multiple
different 3D objects can explain the same image. A model can infer plausible
content, but a better prior does not prove what was actually hidden.

Future route: request additional views, measurements, scans, known templates,
or explicit user choices. Label inferred regions. Even future systems should
avoid guaranteeing exact recovery from insufficient information.

B. Universal one-click production-ready characters

We have not demonstrated a system that reliably turns any arbitrary reference
into clean body topology, layered clothing, independent eyes, a mouth interior,
a tested body rig, and a performance-quality facial rig.

Future route: constrain supported styles, use templates and landmarks, combine
specialist models with conventional tools, and retain artist correction. This
is a strong research direction, not a safe first-release promise.

C. Perfect identity under unrestricted regeneration

New generation can alter a face, shape, costume, or proportions. A fixed random
seed alone is not a general identity guarantee across models and edits.

Future route: preserve accepted meshes and rigs, restrict edit scope, introduce
identity-aware representations, and measure drift. Keep exact asset reuse as
a dependable option even when generation improves.

D. Automatically correct topology from polygon reduction

Decimation changes complexity. It does not inherently create animation-friendly
edge flow, eyelids, mouth structures, clean joints, or separate material parts.
A high-resolution model is not automatically well structured either.

Future route: task-specific retopology, protected regions, topology templates,
rig-aware optimization, and deformation testing.

E. Physically truthful materials and motion from appearance alone

A good-looking texture may bake lighting into its color. A rendered surface does
not necessarily reveal true roughness or hidden geometry. Plausible generated
motion is not proof of correct mass, balance, contact, or mechanics.

Future route: additional observations, explicit material controls, simulation,
constraint checking, and specialist review where truth matters.

F. Guaranteed fully automatic long-form films

This project has not demonstrated an automatic complete episode with consistent
characters, editable sets, good acting, camera continuity, clean audio, and
reliable rendering. Combining individually impressive demos does not establish
that result.

Future route: reusable assets, scene-by-scene planning, human-directed acting,
short acceptance shots, and incremental production automation. Keep the creator
in charge of story and approvals.

G. Zero-cost or instantaneous unlimited computation

Inference, storage, rendering, and data transfer require resources. AI progress
may improve efficiency, but zero cost and unlimited capacity should never be
product guarantees. Complex scenes can remain expensive to render.

Future route: smaller supported tasks, caching, reusable assets, cheaper preview
modes, scheduling, compression, and measured optimization.

H. Commercial clearance created by AI progress

A stronger model does not erase restrictions in source, model weights, training
data, binary libraries, likeness permissions, or provider contracts.

Future route: replacement dependencies, permission, a suitable commercial
agreement, or a different model. Some candidates must remain research-only.

I. Guarantees about future breakthroughs

We cannot honestly promise that every difficult capability will become reliable
by November 2027, November 2028, or a later date. Some can improve quickly;
others may remain expensive or inconsistent for years.

Future route: keep an active research portfolio with bounded experiments and
quarterly evidence reviews. Ship capabilities when their acceptance gates pass.


14. ARCHITECTURE THAT CAN IMPROVE WITH FUTURE AI

Preserve one product system with independently versioned model runtimes.
A proposed expanded architecture is:

  Web studio and optional Blender integration
       -> identity, permissions, projects, and asset versions
       -> durable job management and spending controls
       -> approved model and processing adapters
       -> isolated generation / processing / rigging / scene workers
       -> validation and private artifact storage
       -> browser review and tested exports.

The API, gateway, worker, database, storage abstraction, and web studio already
provide much of the initial skeleton. Add new boundaries only when workloads
require them; do not create many services merely to make a large diagram.

Model adapters should describe supported inputs/outputs, exact runtime and
weight versions, license status, resource needs, and known quality limits.
New engines should compete against the current accepted baseline before use.

Keep old assets readable after a model upgrade. Record enough information to
trace an output; a seed alone may not reproduce it across different hardware
or library versions. Preserve original output bytes and exported versions.

Queue cancellation must distinguish "stop waiting locally" from "remote
computation confirmed stopped." Retry policy must not duplicate unconfirmed
billable generation. Build on the current worker's conservative recovery rules.

Database jobs can remain appropriate initially. Introduce specialized queues,
autoscaling, or GPU scheduling when measured throughput and reliability needs
justify them. Deployment scale should follow evidence and budget.


15. DATA, LEARNING, AND OWNERSHIP

The owner should control the brand, first-party product code, customer
relationships, original designs, and authorized infrastructure. Third-party
software and weights retain their actual licenses. A model-generated output
or a fine-tuned checkpoint does not automatically have exclusive legal
protection or unrestricted commercial rights.

Begin with qualified inference. Do not start by training a general foundation
model from scratch. First learn which errors prevent users from completing
their work.

When there is evidence that data or adaptation can help, create a curated,
licensed dataset with per-asset provenance, allowed uses, identity grouping,
style labels, and permitted derivatives. Split training and evaluation by
underlying asset or identity, not different views of the same object.

Potential specialization topics include stable adult proportions, desired
stylization, reliable clothing structures, rig fitting, and correction of
specific measured geometry errors. Each requires a model-appropriate training
method and a held-out benchmark.

Do not assume a generic image LoRA recipe trains an unrelated 3D architecture.
Do not use customer uploads for training by default. Obtain explicit separate
permission, establish retention and deletion rules, and keep private assets
outside public research examples.

A valuable long-term resource is a rights-cleared collection of asset revisions,
artist corrections, and measured downstream outcomes. It becomes useful only
if the collection is lawful, representative, and connected to specific errors.


16. DEVELOPMENT HORIZONS: NOW, ONE YEAR, TWO YEARS, AND BEYOND

These are conditional planning scenarios. Timing depends on budget, team,
license decisions, infrastructure access, and measured results. A calendar date
does not remove a failed technical or legal gate.

NOW TO THREE MONTHS: prove one complete workflow

Priority: preserve the existing foundation and close the real-generation gap.
Complete candidate runtime/dependency review, a bounded approved qualification,
textured GLB validation, browser inspection, and Blender import. Interview
creators and define supported categories. Prepare a small private pilot.

Exit evidence: a traceable real artifact with measured quality, cost, VRAM,
timing, failure information, and successful supported downstream import.
A single good result is the first gate, not general release acceptance.

THREE TO SIX MONTHS: repeatability and private production trials

Priority: evaluate more permitted inputs; improve failure handling, quality
reporting, cleanup, and cost visibility. Establish a usable asset library and
version workflow. Test template-based character preparation with an artist.

Exit evidence: reproducible supported results, credible cleanup-time measures,
privacy/recovery checks, and pilot creators completing real tasks. If the
engine underperforms, change the candidate rather than disguising failure.

AROUND ONE YEAR: November 2027 planning horizon

Potential product shape: a dependable niche asset studio with one or a few
qualified engines, public identity only if completed, tested exports, spending
controls, and a guided character lane based on known templates or supported
input types.

Candidate additions: better material edits, asset variants, limited body-rig
assistance, team review, and Blender transfer. Paid access is conditional on
billing, privacy, support, and actual unit economics.

Who attempts this: the owner, product/backend and frontend engineers, an
ML/inference engineer, and a technical artist, assisted by AI coding tools.
One person may cover multiple roles, which reduces parallel capacity.

Gate: users repeatedly obtain accepted assets at a sustainable cost. Universal
facial rigging and automatic film production are not required for this gate.

AROUND TWO YEARS: November 2028 planning horizon

Potential product shape: a more capable production workspace for a recurring
cast and reusable locations, with asset variants, tested body motion,
constrained facial assistance, richer scene assembly, and selected multi-view
or local-editing improvements if experiments succeed.

Candidate research: model-specific fine-tuning, identity-preserving edits,
retargeting across supported rigs, and assisted expression preparation.
These are separate workstreams, not automatic consequences of a better
image-to-3D model.

Who attempts this: the core product team plus experienced character/rigging
artists, an animation reviewer, and focused ML research support as resources
allow. Partner with maintainers or specialist vendors where appropriate.

Gate: short scenes can reuse the same assets with accepted deformation and
artist-visible improvements. Unsupported characters remain outside the promise.

THREE YEARS AND BEYOND: 2029 onward research horizon

Potential ambition: more general semantic scene editing, stronger facial
performance assistance, editable world construction, persistent character
representations, and tightly bounded natural-language production workflows.

Investigate longer sequence planning, learned rig corrections, physically
constrained interaction, and specialized model development only when there is
a clear product need, suitable data, and approved research capacity.

Who attempts this: a larger multidisciplinary team or partnerships combining
research, graphics engineering, technical art, animation, and operations.
External AI research can contribute better components, but no outside company
or open-source maintainer has committed to solving our requirements.

Gate: each capability passes its own quality, rights, cost, and reliability
checks. Some ideas may remain experimental indefinitely. We should retain
manual and conventional workflows for those cases.

EVERY QUARTER

Review new research, benchmark promising candidates, revisit license status,
and retire unsuccessful experiments. Ask whether users need the capability,
what measurable gap it closes, and whether integration beats rebuilding it.
Record why an idea is adopted, deferred, replaced, or stopped.


17. WHO WILL BUILD AND EVALUATE EACH PART

The project owner defines the product priorities, approves scope and spending,
controls business accounts, and chooses the creative acceptance standard.
Ownership does not remove the need for specialist expertise.

Product/backend engineer: identity integration, permissions, durable jobs,
asset versions, billing ledger, storage, and reliable APIs.

Frontend/3D engineer: studio interaction, browser performance, inspection,
editing controls, collaboration, and tested downstream integration.

ML/inference engineer: runtime qualification, model adapters, GPU efficiency,
benchmarking, dataset design, and justified adaptation experiments.

Technical artist / character specialist: topology, UVs, materials, rig fitting,
facial structure, skin weights, and practical Blender acceptance.

Animator / creative reviewer: poses, expression quality, dialogue performance,
continuity, camera work, and whether an asset is useful in a real shot.

Operations/security engineer: safe deployment, monitoring, cost controls,
backup/restore, incident handling, and isolation of untrusted processing.

Legal or licensing reviewer: rights and commercial-use questions where terms
are unclear or business exposure makes specialist review appropriate.

AI coding tools can help implement, document, test, and analyze bounded work.
They do not provide GPU hardware by themselves, authorize spending, guarantee
legal clearance, or replace the owner's and artists' acceptance decisions.

For a small budget, keep a small core team and use part-time specialists at
milestones. The calendar must reflect available working capacity. No staffing
or hiring commitment is made by this document.

If "who will try in the future" refers to other companies: research labs,
open-source maintainers, graphics vendors, and animation-tool teams are possible
sources of advances. We should evaluate released evidence rather than predict
which organization will solve a feature or when it will happen.


18. BUSINESS MODEL AND COST DISCIPLINE

Possible revenue approaches, to validate rather than assume:

- Subscription for the workspace and a clearly bounded included allowance.
- Metered generation or processing credits tied to actual resource use.
- Team plans for collaboration, access controls, and shared approved assets.
- Later private deployment or developer API agreements if supportable.

Avoid unlimited GPU promises until there is a credible cost model. Asset
storage quotas, job concurrency, and dollar spending limits solve different
problems; existing quotas are not a complete billing or cost-control system.

Estimate cost per accepted asset using:

  total GPU + CPU + storage + transfer + paid-provider + support cost
  divided by the number of results users actually accept.

Include failed work, cold starts, idle capacity, manual correction, and payment
fees where relevant. Compare revenue with that total rather than only the
headline inference time.

Before charging, define credit reservation, settlement, refunds, disputed
outcomes, and idempotent payment event processing. A local timeout does not
prove that remote computation stopped or that no provider charge occurred.

Set experiment budgets and termination rules before launching paid resources.
Recheck provider prices and credit eligibility when needed. This concept uses
no invented market size, revenue forecast, fixed infrastructure quotation, or
guaranteed time to profitability.


19. SECURITY, PRIVACY, AND DEPENDABLE OPERATION

Security needs to remain part of the asset workflow, especially as processing
and collaboration expand.

- Keep projects private by default and enforce owner/team authorization.
- Isolate model, mesh, and Blender processing from product credentials.
- Reject unexpected external resources and bound file sizes and execution time.
- Avoid executing scripts embedded in imported project files.
- Keep secrets server-side and use scoped, short-lived credentials where useful.
- Add tested account recovery, session handling, deletion, and audit behavior.
- Establish retention and backup/restore procedures with checksum verification.
- Track operational failures and resource leaks, not just successful outputs.

For teams, deletion and sharing need clear consequences for shared assets,
backups, derivative versions, and opted-in training data. These are product
requirements that must be designed, not checkboxes satisfied by a login screen.

User publication and training consent must be distinct from uploading a file
for private processing. A public gallery or marketplace is optional later work,
not a reason to publish customer assets automatically.


20. EXPERIMENTS AND RELEASE ACCEPTANCE

Every significant feature should have an experiment that can fail.

First inference experiment:
One rights-cleared input, exact reviewed source/weights/runtime, bounded compute,
real output, browser review, Blender import, and measured total resource cost.

Repeated asset experiment:
A fixed set of supported inputs including difficult cases, all failures kept,
consistent export checks, artist review, and cleanup-time measurement.

Character experiment:
One controlled base character, defined allowed changes, a set of body poses,
face expressions where supported, and a review of identity and deformation.

Scene experiment:
The same assets reused in two shots with different cameras and lighting,
consistent scale and placement, editable objects, and no unexplained variants.

Operational experiment:
Recover from worker interruption, uncertain submission, storage errors, quota
limits, expired credentials, and invalid files without crossing owner boundaries
or blindly duplicating billable work.

A feature can become available for a declared subset of assets even while
research continues elsewhere. Unsupported inputs should produce an honest
limitation or failure result, not an unrelated substitute presented as success.


21. THE FIRST 90 DAYS OF FOCUSED WORK

The ordering matters more than the calendar. Work can pause at a missing
permission, license verdict, budget, or unsupported capability.

Work block 1: reconcile and preserve
Review live source against stale planning sections. Keep the existing API,
worker, storage, studio, and tests. Establish a short supported-feature list and
an explicit first-customer hypothesis. Record which tasks are already done.

Work block 2: qualify one engine
Complete the exact runtime/dependency review for the current candidate or
choose a better-cleared alternative. Verify dependencies and artifacts. Prepare
repeatable configuration without mixing GPU libraries into the product runtime.

Work block 3: prove the real vertical slice
After appropriate approval, perform one bounded real generation run. Inspect
the textured output in the actual product viewer and Blender. Record geometry,
visual problems, timing, VRAM, failures, and cost.

Work block 4: test repeatability
Use a small permitted input set before expanding toward the planned larger
benchmark. Fix genuine integration defects and track engine limitations.
Choose supported categories from evidence, not the best-looking one-off sample.

Work block 5: create a private creator trial
Have a few relevant creators attempt real tasks. Observe cleanup time and
confusion. Add only the controls needed to complete the supported workflow.
Validate the demand before building a large public subscription system.

Work block 6: establish the character research lane
Ask a technical artist to prepare or select one rights-cleared adult-proportion
base character. Define body and face acceptance separately. Compare a template
route against generated geometry on actual production effort.

Work block 7: decide what deserves expansion
Use user results, quality evidence, and costs to choose between a focused
release, an engine change, further private research, or a narrower product.
No success should be declared merely because the schedule reached day 90.


22. RISKS, ALTERNATIVES, AND STOP DECISIONS

If the current candidate model is too weak, preserve the product foundation and
replace the adapter after review. Do not restart identity, storage, and UI.

If character generation remains unreliable, offer a useful template/import
workflow and keep unconstrained generation experimental.

If facial automation fails, support artist-authored facial rigs and assisted
controls rather than claiming a body skeleton supplies facial animation.

If local GPU operation is uneconomic, evaluate a provider integration with clear
terms and measured costs. This creates an external dependency and may limit
control over weights, latency, and pricing; describe that tradeoff honestly.

If a dependency's rights do not fit the business, replace it, obtain permission,
or stop that path. Do not treat a source license as permission for everything
bundled with the model.

If creators do not save meaningful effort, improve the narrow workflow or
change the target customer before expanding the feature catalogue.

If a benchmark improvement is visually impressive but increases support and
manual correction, assess total task completion rather than celebrating one
isolated metric.

If the team cannot support many services or asset categories, reduce the
supported surface. Maintain a product users can depend on before chasing an
all-purpose autonomous studio.


23. EXAMPLE FUTURE PRODUCTION PROJECT

Consider an original short animation with one recurring adult character, one
small office, and several props.

First, establish an approved character from a rights-cleared source. Review its
face, proportions, clothes, body rig, and any supported expressions. Save the
accepted asset rather than generating a fresh identity for every shot.

Second, assemble an editable office from modular licensed or qualified assets.
Keep a stable scene layout, sensible scale, reusable materials, and separate
objects where interaction is required.

Third, prepare a 10- to 30-second test shot. Block body motion and camera work,
review contact and clipping, add facial performance only where supported, and
render a low-cost preview before final output.

Fourth, measure actual human effort, render time, failures, and continuity.
Correct the reusable assets and preserve the approved revisions. Only then
attempt a longer sequence.

The earlier ambition of ten roughly 30-minute episodes remains a long-term
creative use case. It is not a sensible initial acceptance test for a new
platform. At 24 frames per second, that ambition represents 432,000 final
frames before revisions; actual cost depends on scene complexity and measured
render performance. AI-assisted asset creation does not remove production
planning, acting, editing, sound, or rendering work.

A useful future studio reduces that repeated effort while keeping the creator's
assets and decisions coherent across the production.


24. DEFINITION OF SUCCESS

Near-term success:
A creator can obtain a real supported 3D result, understand its limitations,
open it in the viewer and Blender, retain private access, and repeat the task
without unacceptable cost or failure.

Product success:
Real customers repeatedly complete their intended asset tasks with less cleanup
and better continuity, while the operator can support the service sustainably.

Long-term success:
Creators maintain their own reusable characters, props, and worlds, using AI
assistance where it works and dependable conventional tools where they are
better. New models can improve the system without invalidating existing assets
or forcing the owner to rebuild the product.

This is an ambitious project with a useful existing foundation. Its strongest
path is to finish and measure one real workflow, preserve the work already done,
and grow toward the larger animation vision through independently verified
capabilities.
